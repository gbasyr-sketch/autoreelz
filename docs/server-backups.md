# Серверные резервные копии AUTO REELZ

Поручение владельца14.10.2026: использовать имеющийся Яндекс Диск (свободно более1ТБ), шифрование до отправки, копирование каждый час,24 часовые/7 дневных/4 недельные/3 месячные, несколько локальных версий, ежемесячная проверка восстановления и статус в manager. Расписание включать только после первой полной проверки. Это текущий контракт новой реализации; фактическое состояние и выпуск — status.md.

## Область

Только rootless-проект autoreelz2026-release на91.200.150.79. В копию входят PostgreSQL нового магазина/роли с проверочными значениями паролей внутри зашифрованной копии, uploads, ai_image_assets с исходниками/вариантами/receipts, текущий Git-релиз, статическая /muzey/ и другой public, server.env, собственный origin Nginx-конфиг и origin TLS. Данные и настройки прежних проектов не читаются. Системный Docker, ISPmanager, другие сайты и Amnezia не изменяются.

Шлюзы NL остаются отдельной зависимостью; их секреты/сертификаты и инструкции восстановления нужно хранить отдельным защищённым набором. Основной магазин может быть восстановлен с выключенными ИИ-запросами. Копия RU не является образом всего сервера или backup VPN. Прежние предоперационные DB-only дампы не удаляются.

## Согласованная точка

scripts/backup/store_backup.py сначала копирует файлы в закрытый временный stage. Затем под короткой SHARE-блокировкой таблиц экспортирует PostgreSQL snapshot, повторно копирует uploads/ai_image_assets и получает pg_dump и отпечатки таблиц из той же точки. Чтение витрины остаётся доступно; записи могут кратко ожидать. LOCK NOWAIT отменяет попытку при занятых таблицах, без вытеснения работающего запроса. Текущие queued/preparing/running image jobs и running text requests откладывают копию; оплаченные запросы не прерываются.

Снимок транзакции создаётся после блокировки таблиц. Блокировка обновлений схемы согласована с используемым migration advisory lock. Смена ревизии приложения или server.env во время захвата отклоняет копию. Перед принятием сверяются наличие файлов Directus и оба формата результатов ИИ с их сохранёнными хэшами. После захвата блокировки освобождаются; шифрование/загрузка выполняются без удержания БД. Время блокировки измеряется. При росте БД свыше1ГиБ текущий ограниченный процесс остановится с предупреждением: требуется пересмотр и переход к подходящему физическому backup/PITR.

## Хранение и доступ

Restic0.19.1 создаёт зашифрованный локальный репозиторий; rclone1.75.2 переносит снимок в закрытую папку AUTO-REELZ-backups/autoreelz2026. Бинарники закреплены и проверены по официальным SHA256, установлены только в /srv/autoreelz2026/bin/backup; глобальные пакеты не меняются. У репозиториев закреплены ID и общие параметры разбиения данных. Существующий неизвестный репозиторий не переинициализируется.

Пароль шифрования, OAuth и пароль приложения WebDAV находятся только в shared/backup-private (0700/0600) и закрытых локальных материалах. Пароль восстановления дополнительно передаётся владельцу локальным закрытым файлом, не сообщением чата и не Git. Рабочие команды ограничены папкой копий. Не использовать rclone cleanup, sync корня Диска или очистку общей корзины. Через WebDAV удаление необратимо; retention разрешён исключительно внутри собственного репозитория по согласованной политике хранения.

14.10.2026 нативный REST backend Яндекса отвечал410 на операции с файлами при успешном OAuth и чтении квоты. Это также зарегистрировано в [rclone#10067](https://github.com/rclone/rclone/issues/10067). Выбран официальный [WebDAV](https://yandex.ru/support/yandex-360/customers/disk/web/ru/webdav): https://webdav.yandex.ru, TLS с проверкой сертификата, vendor=other, отдельный пароль приложения «Файлы WebDAV». Сначала проверен PROPFIND, затем создана новая закрытая папка; чужая существующая папка автоматически не переиспользуется. Первоначальные500 при создании папки оказались временными: создание и инициализация затем прошли. Наличие доступа не заменяет проверку загрузки/восстановления. OAuth сохранён для обратимости, но рабочая передача использует WebDAV.

Удалённая копия считается успешной только после появления ожидаемого снимка на Диске. Незавершённая передача остаётся в очереди; повтор не перезаписывает существующие версии. После аварии между локальным сохранением и записью очереди недоставленные локальные снимки обнаруживаются заново. Локальное удаление старых копий запрещено при недоставленных снимках. Временные незашифрованные файлы в stage доступны только root и удаляются после обработки; при аварийном завершении могут остаться до следующей попытки под теми же ограничениями.

## Расписание и проверка

Собственные systemd units — infra/backup: часовой backup, ежемесячный verify, еженедельный retention. Часовой сервис повторяет временные ошибки через5 минут. При занятом общем файловом lock задания ждут повторного запуска; одновременно два процесса не копируют/не удаляют репозиторий. Внешние сообщения не отправляются: в manager доступны свежесть копии и результат проверки.

Verify скачивает снимок с Яндекс Диска, проверяет данные restic/полный manifest файлов и восстанавливает PostgreSQL в новый disposable-контейнер без сети и host-портов. Сверяет отпечатки всех таблиц, права, фото и исходные PNG/WebP. Directus на клоне не запускается, OIG повторно не активируется. Удаляется только созданный тестовый контейнер с проверенным ownership label и его том, временные расшифрованные файлы удаляются. Это проверка БД/файлов/прав; не полная автоматическая установка чистого VPS и не проверка реальных оплат/писем.

Успешная проверка записывает маркер verified-recovery.json. Без него retention и включение расписания запрещены. Политика remote:24 часовые,7 дневных,4 недельные,3 месячные; local: последние3. Группировка по host,paths, без уникального run-tag. Перед удалением проверяются repository ID, собственный host/tag и отсутствие недоставленных копий. Ошибка restore не скрывается последующей успешной загрузкой.

## Статус и восстановление

Публичных архивов и кнопки восстановления нет. GET /api/manager/backup-status требует штатную staff-сессию; отдаёт только разрешённые даты/состояния/объём. В web подключается только read-only каталог shared/backup-status. Секреты, пути, stdout/stderr и данные заказов в API не попадают. Отсутствующая/повреждённая сводка не объявляется успешной копией. Копия старше2 часов или проверка старше35 дней требуют внимания.

Живую базу автоматически не восстанавливать. При реальном инциденте сначала остановить записи и внешние действия, выбрать проверенный снимок, оценить потерю новых операций и сверить оплаты/отправления. Затем отдельное решение владельца на восстановление. До продаж следует согласовать меньший предел потери данных для заказов и отдельный PITR/WAL-план; часовой logical dump не равен непрерывному журналу изменений.

## Команды сопровождения

На собственном RU-сервере от root: `/usr/bin/python3 /srv/autoreelz2026/ops/backup/store_backup.py backup`, `verify` или `retention`. Общий файловый lock не допускает конкурирующие операции. Диагностика закрыта в backup-private; не копировать stderr/config в публичные отчёты. `capture` и `verify-local` позволяют проверить локальный зашифрованный снимок при недоступном облаке: они не ставят маркер внешней проверки и не разрешают расписание/retention.

Units находятся в infra/backup; установленный код и его SHA256 — ops/backup/version.json. После изменения runner сначала проверять его отдельно, затем обновлять только собственные units. Не включать таймеры до появления verified-recovery.json с external=true. Начальный ручной запуск service проверяет также ограничения systemd; расписание само по себе не доказывает успешную копию.

Для восстановления на чистом сервере понадобятся доступ к Диску и отдельный пароль restic из файла владельца. Сначала `restic check --read-data` и восстановление в закрытый временный каталог, сверка manifest/репозитория, запуск проверочного PostgreSQL без сети. После отдельного разрешения на переключение — настройка нового rootless-проекта, восстановление ролей/БД и конфигурации, перенос томов под правильные UID/GID **внутри rootless namespace** (не общий chown всех файлов на UID1018), проверка origin TLS/прокси и запуск проверенного Git-релиза. Бюджеты, история запросов и приватные исходники восстанавливаются вместе с БД/томами; не создавать новые независимые лимиты. Перед включением внешних действий сверить оплаченные/неопределённые запросы и торговые операции после точки копии. Полная процедура чистого VPS пока не прошла отдельную аттестацию.
