# Эксплуатация и восстановление

> Backup/restore ниже относятся к локальному Compose-проекту. Серверное зашифрованное резервирование — [server-backups.md](server-backups.md); диагностика/выпуск/откат — [server-staging.md](server-staging.md). Проверенное состояние внешних копий и расписания — [status.md](status.md).

Подготовлено на этапе 7, 23.09.2026. Скрипты `backup-local`, `restore-drill`, `ops-check` сейчас привязаны к **новому локальному** проекту `autoreelz2026-new`. Они не управляют будущим сервером и старыми проектами. Перед работой используйте Node из .node-version.

## Резервная копия

```sh
node scripts/backup-local.mjs --create
```

Скрипт проверяет имя проекта/БД, запоминает работающие web/worker/CMS и кратко останавливает только их. PostgreSQL продолжает работать. Если остались сторонние подключения ar_app/ar_cms, операция прекращается и прежние сервисы запускаются обратно. Затем сохраняются custom pg_dump, роли без паролей, uploads, локальная environment.env, список миграций/хешей, контрольные суммы файлов и отпечатки строк всех публичных таблиц. Это согласованная точка БД и файлов; одного pg_dump недостаточно для согласованности с изменяемым uploads.

Каталог `private/backups/<время>` —0700, файлы —0600, в Git не входят. Дамп содержит настройки OIG и частные данные; environment.env содержит секреты. Это **локальная незашифрованная** копия с файловыми ограничениями, не внешний архив. Не отправлять её в чат, Git или общую облачную папку. Для сервера нужны отдельное зашифрованное хранилище и ключ восстановления.

Manifest помечается complete только после успешной копии. При обычной ошибке сервисы запускаются в finally. При аварийном завершении процесса/потере питания проверить `docker compose -p autoreelz2026-new ps` и вернуть web/worker/CMS командой `start`; incomplete-копию не использовать. Повторный backup блокируется каталогом private/backup.lock. После аварии сначала убедиться, что копирование не идёт и сервисы возвращены, затем удалить только этот пустой lock-каталог. Отпечатки string_agg рассчитаны на текущую небольшую локальную БД; для крупной production-базы нужен потоковый verifier/иной план объёмов.

## Репетиция восстановления

```sh
node scripts/restore-drill.mjs private/backups/<время>
node tests/restore-guards.mjs private/backups/<время>
```

Принимаются только собственные доверенные копии внутри private/backups, без выхода через symlink. До создания контейнера проверяются SHA256 дампа/ролей/секретов/медиа. Дамп SQL способен выполнять команды — чужие архивы этим инструментом не восстанавливать.

Создаётся новый PostgreSQL той же версии/digest, без host-портов и с `--network none`. Восстановление идёт в отдельную ar_qa_restore с `--single-transaction --exit-on-error`. Сверяются строки всех таблиц, ключевые права ar_app/ar_cms и побайтовые хеши медиа. Оригинальная БД и uploads не перезаписываются; Directus на клоне не запускается, лицензия не активируется. Контейнер с его новым томом и временные файлы удаляются.

Фактическая проверка:85 таблиц,5850 строк и 2 файла совпали;11 секунд локального drill. Это не обещание RTO сервера: скорость/размер реальных данных и скачивание внешнего архива ещё не проверены. Роли восстановлены без паролей; SQL-права проверены, вход приложения с секретами на новом сервере проверяется отдельно после назначения новых паролей.

## Наблюдение

```sh
node scripts/ops-check.mjs
```

Код выхода 0 — текущие проверки прошли,1 — требуется внимание. Проверяются четыре healthy-сервиса, heartbeat worker не старше 60 секунд, просроченные выделения склада, manual_review, старые pending-письма/уведомления, failed-уведомления и завершённая копия за 24 часа. Вывод содержит только агрегаты, без email, адресов, OTP и тел заказов. Метрики не опубликованы через HTTP; уведомления наружу не отправляются. Пороги — начальное техническое предложение, а не согласованный SLA.

На сервере дополнительно нужны свободный диск/иноды, ошибки TLS/5xx, доступность внешних API/лицензии, время выполнения jobs, возраст внешних копий и контроль успешного restore. Предложение: ежедневная копия плюс копия перед миграциями,7 ежедневных/4 недельных/3 месячных, проверка восстановления ежемесячно; RPO до 24 часов подходит только после согласования потери данных владельцем. Для заказов с меньшим RPO выбрать PITR/WAL или более частые копии. Расписание, платное хранилище и внешние оповещения пока не включены.

## Версия и откат

`node scripts/build-release.mjs` требует чистый Git, запускает Astro check и проверку revision, собирает образ с полным commit SHA, OCI-label и APP_REVISION. Образ и manifest сохраняются локально; registry push и размещения нет. `/health` возвращает только ok/revision, при отказе БД —503. Сравнить SHA в ответе с manifest; успешный health не заменяет покупку и sandbox-проверки.

Выпуск: проверить tagged commit, migration checksums, копию/restore и предыдущий image digest. На новом сервере применять миграции один раз в согласованное окно, затем выпускать web/worker одной версии и проверять health/покупку/очереди. Локальный setup-local не является production-deployer: он привязан к другой среде и может добавлять демо-контент.

Откат приложения — предыдущий сохранённый image digest, только если он совместим с текущими миграциями. Применённые SQL-файлы не менять и не удалять колонки «для отката». Откат БД к копии теряет новые записи; при настоящих платежах сначала остановить запись и сверить PSP/заказы/возвраты, затем принять отдельное решение. Production-restore не автоматизирован этим локальным drill.

Основа: [PostgreSQL17 pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html) и [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html). Конфигурация соответствует проверенной установленной версии 17.11.

## Очистка анонимных сессий и пустых корзин (037, опубликовано16.10)

Опубликовано16.10: appdc6e42d/001–037. Первый автоматический проход и часовой guard проверены, удалено0пар: подходящих кандидатов пока нет. При последующих выпусках сохранять037 и состояние расписания. Применённые001–036 не менять. Миграция создаёт индексы, read-only представление кандидатов, состояние расписания и узкую функцию; сама миграция ничего не удаляет.

Консервативный фильтр: анонимная сессия без customer_id, expires_at раньше текущего времени на30дней; связанная корзина version=0 без строк; нет заказов, checkout batches, даже истёкших quotes, попыток входа, согласий/privacy events и результатов команд cart/checkout/pay/cancel/privacy. Срок cookie30дней не сокращается: обычная нетронутая сессия будет кандидатом примерно через60дней после создания. Сессии без корзины и ранее изменённые, но опустевшие корзины остаются. При новых session-scoped командах проверять дополнение фильтра. Это не общая политика удаления клиентских/юридических данных.

Раз в час commerce-worker после торгового цикла вызывает ar_cleanup_empty_sessions: максимум200 пар, READ COMMITTED, advisory-lock320260937, FOR UPDATE с SKIP LOCKED на обеих родительских строках и повторная проверка после блокировки. Только затем явно удаляются пустая корзина и сессия, одной транзакцией. Новые CASCADE/SET NULL/SET DEFAULT зависимости блокируют функцию; неожиданный restrictive FK откатывает весь пакет. Заказы, платежи, склад, клиенты, избранное, входы, согласия, почта и журналы не удаляются/не изменяются. Прямых DELETE-прав на сессии/корзины у ar_app нет; PUBLIC не может выполнить функцию.

Таймаут запроса5с/блокировки500мс; ошибка очистки не прерывает торговый цикл/heartbeat, в логе только код ошибки. После ошибки отдельная пауза1час. ar_session_cleanup_state хранит последнее успешное время, число удалённых пар и суммарный счётчик; оно фиксируется вместе с удалением и переживает рестарт. Отдельных внешних уведомлений нет. Нулевой успешный проход тоже занимает часовой слот.

После037 read-only проверка: `node scripts/session-cleanup-preview.ts` в подготовленной локальной среде; в контейнере доступна `node --input-type=module -e "import('./src/server/session-cleanup.ts').then(async m=>{console.log(await m.sessionCleanupPreview());await(await import('./src/server/db.ts')).getPool().end()})"`. Скрипт не имеет apply-флага и публичного endpoint. Перед выпуском сохранить backup и сверить количество кандидатов; индексы создаются обычной транзакционной миграцией, длительность зависит от объёма БД.

Для немедленной остановки очистки без остановки торговли отозвать только EXECUTE этой функции у ar_app (в worker появится отдельная ошибка и часовая пауза); возобновление — вернуть EXECUTE. Прежнее приложение84bf555 совместимо с добавочной037 и просто не запускает cleanup. При откате не восстанавливать всю БД/env и не пытаться воссоздавать старые анонимные визиты поверх новой истории. Обычный DELETE освобождает место для повторного использования PostgreSQL; мгновенное уменьшение файла БД не обещается, VACUUM FULL не требуется этой задачей.


## Лимит создания гостевых сессий (опубликован16.10, app10eb244)

`src/server/session-rate-limit.ts`:60 новых сессий в фиксированном минутном окне и600 в часовом. Учитывается только успешное атомарное создание session/cart; действительная cookie обходится без счётчика. Источник IP — adapter clientAddress за уже настроенным доверенным proxy, не сырые заголовки. IPv4-mapped приведён кIPv4, IPv6 объединён по/64; отсутствующий/некорректный IP попадает в общий защищённый unknown. Ключи HMAC, сырые адреса не хранятся. Ошибка429 с Retry-After, no-store/noindex; statics/health/discovery и YooKassa webhook сохраняют исключения middleware. Logout всегда отзывает старую сессию, даже если новую создать нельзя.

Общие NAT делят лимит новых посещений, действующие корзины не блокируются. Лимит не заменяет edge-защиту от распределённой нагрузки. Используется существующая ar_rate_limits;037 относится только к отдельно подготовленной уборке, для limiter не нужна. При выпуске нельзя автоматически включать накопленные непубликованные изменения/037 без отдельного допуска.


Уточнение выпуска16.10: к моменту публикации limiter очистка037 уже была включена другой работой. Владелец разрешил сохранить её автоматическое состояние; ручных вызовов не было. Историческое требование отдельного допуска выполнено; limiter не требует повторной миграции/сброса cleanup-state.
