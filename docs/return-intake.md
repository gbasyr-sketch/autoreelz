# Приёмка возвращённых товаров

Опубликовано15.10.2026 по поручению владельца. В карточке заказа добавлен отдельный блок: сначала зарегистрировать фактически полученную посылку, затем после личной проверки вернуть на склад только пригодное количество. Получение и возврат денег не увеличивают остаток автоматически. Команды разрешены только в local-test/staging; production закрыт. Выпущен проверенный app6ff750c, схема001–033.

## Работа владельца

1. В блоке «Приёмка возвращённых товаров» указать трек обратной посылки или уникальный номер своего акта приёма, количество фактически полученных SKU и примечание. Подтвердить приёмку. Один трек/акт на заказ регистрируется один раз; регистр номера и лишние пробелы не создают другую посылку. Если трека нет, номер акта задаёт владелец, а не случайный генератор формы.
2. Полученный товар пока держать отдельно от продажи. В интерфейсе видны ожидающее проверки, уже принятое на склад и оставленное вне продажи количества. Проверка начинается без предвыбранного прихода: пригодное количество нужно указать явно.
3. По каждой полученной позиции указать, сколько пригодно к продаже. Остальное фиксируется как оставленное вне продажи: повреждённое, некомплектное либо требующее дальнейшего решения. Записать результат осмотра и подтвердить точное количество для прихода.
4. После сохранения пригодные физические SKU поступают на склад одной транзакцией. Резервы других заказов не сбрасываются. Проверка и движения остаются в истории; повтор не создаёт новый приход. Изменение уже зафиксированного решения требует отдельной обоснованной корректировки, не редактирования журнала.

При ошибке связи состав и ключ сохраняются в sessionStorage. Перезагрузка страницы не пересчитывает запрос по новым остаткам; кнопка «Повторить тот же запрос» уточняет прежний результат. Пока исход неизвестен, новые операции и редактирование этой приёмки заблокированы. При недоступном хранилище отправка не начинается, при ошибке его очистки после принятия также остаётся безопасный повтор с прежним ключом.

Форма принимает только SKU исходного заказа с подтверждённым складским списанием. Неизвестную/другую деталь нельзя подменять похожим SKU: оставить отдельно и сначала сверить происхождение. Возвраты денег, исправление исторических ручных движений и повторная проверка отложенного товара не выполняются этой командой.

## Обычные товары и комплекты

Состав берётся из сохранённого заказа и ar_order_components, не из текущего состава каталога. Одна и та же физическая деталь, проданная отдельно и внутри комплекта, показывается одним SKU с источниками. Например, отдельная деталь A×1 и два комплекта A×2+B×1 дают максимум A×5 и B×2 для приёмки. У виртуального комплекта собственный остаток не создаётся.

Можно принять неполный комплект по фактически вернувшимся составляющим. Финансовый возврат при этом по-прежнему работает с купленными позициями/целыми комплектами из031; физический и денежный состав не подменяют друг друга. В этой версии нет автоматического пересчёта суммы возврата по результату осмотра.

## Откуда берётся допустимое количество

Заказ должен иметь allocation_state=settled и быть отправленным/полученным. Неоплаченный резерв, отменённое/освобождённое выделение и оплаченный заказ у поставщика без физического прихода не создают товар для возврата. Денежный статус review не препятствует приёмке уже отправленных и списанных SKU.

Для каждого SKU берётся минимум из сохранённого количества заказа и фактического чистого списания его прежними складскими операциями. Новые приходы с ключом return-intake не уменьшают этот исходный бюджет. Все зарегистрированные полученные единицы, включая оставленные вне продажи, расходуют бюджет: одну деталь нельзя принять повторно другой посылкой.

Если снимок состава, ar_order_components или история движений расходятся, новые операции блокируются до сверки. История приёмок остаётся доступной. Ранее вручную возвращённые товары не импортируются автоматически; перед первым использованием по старому заказу нужно сверить его прежние движения, чтобы не повторить ручной приход без связи с заказом.

## Транзакции и история

Миграция033 добавляет ar_return_receipts/lines и ar_return_inspections/lines. Идемпотентный запрос и проверка бюджета сериализуются по блокировке заказа в READ COMMITTED. Трек/акт уникален в пределах заказа; одна посылка получает только одну итоговую проверку. Совпадающая команда другого оператора/с другим ключом возвращает прежний ID, иной состав или результат вызывает конфликт.

Проверка охватывает все полученные SKU: пригодное плюс оставленное вне продажи равно принятому. Приход блокирует SKU в общем порядке, пишет положительные stock_delta и нулевые reserved_delta с уникальным ключом `return-intake:<inspection-id>`. При ошибке любого SKU откатываются вся проверка, движения и изменения остатков.

Журнал доступен приложению только для SELECT/INSERT; UPDATE/DELETE запрещены. Заголовки принудительно получают номер создающей транзакции, строки можно добавить только в этой же транзакции. После COMMIT нельзя дописать позиции в завершённую приёмку/проверку. Отложенные проверки подтверждают полноту состава и соответствие движений. Складские записи return-intake также нельзя дописать позже или переписать. Сотрудник, время регистрации и примечание сохраняются.

Ни получение, ни осмотр не вызывают PSP, SMTP, СДЭК или ИИ, не меняют факты оплаты/финансовые возвраты, не закрывают разбор заказа. Заказ остаётся manual_review. Приёмка не заменяет проверенные условия возврата денег после доставки из031.
