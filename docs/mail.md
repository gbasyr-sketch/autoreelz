## Контракт

- Nodemailer10.1.1, локальная зависимость с собственными типами и без дополнительных runtime-зависимостей. Fixed SMTP smtp.timeweb.ru:465, TLS с проверкой сертификата, отправитель/Reply-To sales@autoreelz.ru, имя AUTO REELZ. Отладка/SMTP-трафик/сырые ошибки не логируются, файлы/URL/вложения/HTML из входных данных не загружаются. Пароль никогда не включается в Git/образ/JSON API.
- `MAIL_PROVIDER=simulation` по умолчанию. `timeweb-smtp` доступен в действующем тестовом окружении. По умолчанию MAIL_RECIPIENT_POLICY=allowlist требует точного MAIL_ALLOWED_RECIPIENTS. По поручению владельца добавлен all-new: любой корректный email, но только для сообщений не старше MAIL_NEW_MESSAGES_FROM. Без корректного момента включения all-new блокируется. Это не рабочий режим массовой отправки. `MAIL_OWNER_RECIPIENT` задаёт адрес владельца. На сервере `SMTP_PASSWORD` передаётся только commerce-worker; web/image-worker его не получают.
- Новые письма получают provider при создании в той же SQL-транзакции, что код/заказ/событие. Старые записи остаются simulation, переназначение запрещено триггером029; начального replay нет. Снимок SMTP (получатель/тема/текст/ключ/Message-ID/срок/источник) неизменяем. Заказ не откатывается из-за недоставленного письма.
- Письма покупателю: код входа, создание заказа, подтверждение предзаказа, тестовая оплата, отправление с треком, получение/отмена. Пока торговля staging, письма о заказах честно тестовые. OTP содержит код/срок и предупреждение не передавать его другим; статус симулятора в настоящий текст не подставляется.
- Внутренние email-уведомления используют существующие события заказа; MAX пока остаётся имитатором. Создаётся одна SMTP-запись на исходное уведомление. Нет получателя — исходное уведомление failed без внешней отправки; изменение настройки не рассылает старые события.
- Worker выбирает одну SMTP-запись за тик с lease90секунд. Сеть вне SQL-транзакции. Одновременные workers не отправляют одну запись дважды; одинаковый ключ постановки не создаёт вторую запись. SMTP не гарантирует идемпотентную доставку: один Message-ID лишь стабилен при безопасных повторах, а не обещание dedup у получателя.
- Подтверждённые временные отказы4xx, DNS/таймаут установления соединения повторяются максимум3 раза с задержкой1/2минуты. Явный5xx/ошибка авторизации — failed. Разрыв после DATA, общий socket timeout/CONN с неизвестной стадией и потерянный worker — uncertain; автоматического повтора нет. Сырые provider responses, адреса и секреты в last_error не сохраняются.
- `delivered` для SMTP означает принятие сервером, подтверждается отдельным smtp_accepted_at; это не гарантия попадания во входящие. Реальную доставку проверяем отдельно. Для simulation delivered сохраняет прежнее значение локальной имитации.
- OTP не отправляется после expires_at/погашения challenge; неподтверждённый код живёт10минут. Обычная очередь живёт1день. Перед отправкой повторно проверяются политика адресатов и время создания. В allowlist несогласованный OTP отклоняется до challenge; all-new допускает любой корректный адрес, сохраняя прежние лимиты OTP и сроки.
- `/api/manager/mail-status` требует staff и no-store, показывает только счётчики и безопасные метаданные/коды ошибок. Действующий тестовый inbox manager показывает только simulation: настоящие SMTP-коды туда не выдаются. Retry внутреннего уведомления может повторить только определённый failed, не uncertain/expired/исчерпанные3попытки.
