# Сроки и снимки условий заказа —15.10.2026

Доработка тестового оформления опубликована15.10.2026, миграция027. Точный текущий SHA — [status.md](status.md). Реальные платежи/чеки/письма не включены. Документы опубликованы отдельно через manager по прямому поручению владельца.

## Что изменилось

- При проверке корзины сохраняется конкретная предельная дата получения: конец возможного срока оплаты, до3 рабочих дней подготовки и верхний срок тарифа СДЭК в рабочих днях. Дата вычисляется по Москве и сохраняется в расчёте, затем в заказе; после оплаты не пересчитывается. Для ПВЗ это дата доступности товара и уведомления покупателя по оферте.
- Встроен проверенный пятидневный производственный календарь РФ2026. Если расчёт пересекает границу известного календаря, срок тарифа отсутствует или доставка ручная, автоматическая дата не придумывается. Менеджер согласует дату до оплаты. Для предзаказа дата всегда отдельная.
- Обычный заказ без готовой суммы/даты остаётся открытым без резерва и таймера. После согласования доставки сервер повторно проверяет и резервирует наличие транзакционно, открывает полные30минут. Для предзаказа сохраняется прежнее однократное списание при подтверждении; теперь требуется дата получения. Версия доставки меняется вместе с условиями.
- Менеджер указывает согласованную дату получения в форме доставки/предзаказа. Нельзя открыть оплату нового заказа без даты или задать прошедшую дату; пользователь видит её до оплаты. После начала платежа/оплаты дата защищена от изменения на уровне БД. Старым заказам дата и принятие новых условий не приписываются.
- Полный текст оферты, его версия и SHA256 включены в неизменяемый снимок подтверждения. Доступны до оформления и в истории заказа. Файл `src/lib/retail-offer.json` генерируется `node scripts/build-offer-snapshot.ts` из `docs/legal-pages/offer.html`; тест проверяет совпадение. Текстовые узлы выводятся безопасно, без вставки HTML.
- ЮKassa: `captured_at` из проверенного ответа API сохраняется как `provider_paid_at`. В нашем одностадийном сценарии `capture=true` это позволяет отличить время успешного платежа от задержки уведомления. Своевременный платёж при ещё сохранённом резерве проводится без ложного истечения. Если резерв уже освобождён или заказ отменён, остаётся ручная проверка без повторного списания; причина прямо сообщает о своевременности платежа. Отсутствующее/недостоверное время не объявляется доказательством своевременности. Повторное изменение сохранённого времени запрещено.

## Границы готовности

Это ещё не переключение checkout на реальные договоры: действуют явно тестовые условия, а копия оферты вложена для проверки будущего процесса. Production остаётся закрыт в конфигурации. Миграции025–027 выпущены; перед реальными продажами требуется включение настоящих платежей/чеков/уведомлений и замена тестового подтверждения действующей офертой. Снимок должен совпасть с окончательной опубликованной редакцией на момент запуска.

Ручная форма фиксирует дату как уже согласованную менеджером. Отдельного механизма согласования через переписку в этой доработке нет; нельзя выдавать техническое заполнение даты за полученное согласие покупателя. Для календаря2027+ нужна отдельная проверенная таблица; до неё используется ручная дата. График конкретного ПВЗ/курьера и региональные особенности учитывать при ручном согласовании. Подтверждение выдачи, реальные сообщения и чеки остаются отдельными задачами.
