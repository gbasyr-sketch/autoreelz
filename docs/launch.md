## Порядок подключения

1. Подключить тестовую ЮKassa и выбрать чеки; согласовать tax/receipt-контракт. Сохранить снимок чека с конкретным заказом и версией доставки. Выделить создание provider payment и обработку подтверждённого статуса; сверять ID/сумму/RUB/заказ, сохранять идемпотентность и правила поздней оплаты. Не переносить HMAC локального имитатора на реальный webhook.
2. Подключить sandbox СДЭК: отправитель, населённый пункт/ПВЗ, масса и проверенные габариты. Ошибка/таймаут → ручное уточнение без вымышленной стоимости; два заказа получают разные доставки. Нормализовать реальные события в существующую историю/ручной override.
3. Подключить почту/MAX к outbox с устойчивыми ключами, попытками и контролем повторов. Первые внешние сообщения — только утверждённым тестовым получателям после отдельного поручения. В MAX достаточно номера/события/защищённой ссылки без адреса покупателя.
4. Закрыть реальные данные каталога, документы и доступы. Выбрать сервер, восстановление и мониторинг. Повторить покупку на конфигурации выпуска, включая редкие/поздние события.
5. Показать конкретный SHA/образ, sandbox-результаты, план DNS/TLS и отката. Получить отдельное подтверждение публикации/денег/сообщений; только затем активировать нужные действия.

## Серверный шаблон

`infra/release/compose.yaml`, `Caddyfile`, `environment.example` — проверенные по синтаксису заготовки для отдельного проекта `autoreelz2026-release`. Образы БД/CMS/Caddy закреплены digest; приложение задаётся RELEASE_IMAGE после проверки commit. Новые пароли генерируются отдельно. БД и приложение не имеют host-портов; CMS только 127.0.0.1, внешний вход витрины — Caddy80/443. Административный HTTPS-доступ к CMS ещё нужно настроить под выбранный сервер/домен; один сырой HTTP-туннель не считать готовым входом с Secure-cookie.

Caddy обслуживает только autoreelz.ru, запрашивает HTTPS после согласованного размещения, заменяет forwarded host/proto. Astro доверяет лишь autoreelz.ru по HTTPS; чужие forwarded host и Origin проверены отрицательными тестами. Сжатие включено только для статических ресурсов: HTML содержит CSRF/сессионные данные. Персональный cache-control не ослаблен. TLS-сертификат пока не выпускался; проверка Caddy выполнена с отключённой сетью.

Не запускать этот Compose как готовый магазин: нынешний production-режим намеренно блокирует локальные торговые/почтовые имитаторы, а реальные адаптеры ещё не выбраны. До подключения провайдеров применение шаблона не даст работоспособную покупку. Bootstrap, миграции, private HTTPS CMS и OIG выполняются отдельными проверяемыми шагами, без демосидов.

## Источники и ограничения

Astro Docs и Context7 доступны и использованы; правила сверены с установленными Astro7.3.3/@astrojs/node11.1.6. [Astro allowedDomains](https://docs.astro.build/en/reference/configuration-reference/#securityalloweddomains), [Node adapter](https://docs.astro.build/en/guides/integrations-guide/node/), [Caddy HTTPS](https://caddyserver.com/docs/automatic-https), [compression](https://caddyserver.com/docs/caddyfile/directives/encode).

Владелец выбрал ЮKassa. Подготовлен отдельный клиент и файл ключей — [yookassa.md](yookassa.md). По текущей [документации тестирования](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing) тестовые способы ограничены картой/ЮMoney; не обещать полный sandbox СБП и настоящий фискальный чек. Подтверждение СБП может потребовать отдельного контролируемого реального теста после разрешения владельца. Реальный sandbox ещё не вызван: ключей нет.

Документация СДЭК: [официальный портал API](https://apidoc.cdek.ru/). В этой среде портал отдаёт JS-оболочку; endpoint-схемы/ключи по памяти не придумывались, реальный API-запрос не выполнялся. Правила MAX/email/OpenAI уточняются под выбранные аккаунты; ссылки и прежние договорённости — integrations-stage-5.md.

Google Rich Results Test и итоговый фид проверить с доступом/реальными товарами. Мобильный LCP SKU2.573 с из этапа 6 требует повторного замера на сервере/фото; локальная подготовка не подтверждает полевой INP или готовность к продажам.
