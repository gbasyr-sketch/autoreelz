# Архитектура — предложение этапа 0

Стек из брифа: Astro SSR + TypeScript, PostgreSQL, Directus. Реализации и миграций пока нет. Версии — [versions.md](versions.md).

## Границы

Astro отдаёт HTML каталога и выбранного SKU, обслуживает сессию и серверные команды покупки. Простой клиентский TypeScript — для интерактивности; React не нужен по умолчанию. Directus управляет каталогом, контентом и формами владельца. PostgreSQL — источник истины каталога, торговых операций и событий. Фоновый worker из того же проекта обрабатывает сроки, inbox/outbox и повторные попытки.

Торговые команды — один серверный модуль, общий для storefront API и действий сотрудника. Directus показывает защищённые данные и вызывает команды через небольшой адаптер с проверяемой серверной личностью сотрудника. Ни Flow из нескольких независимых CRUD-запросов, ни клиент не выполняют складскую транзакцию. Публичный CRUD заказов/остатков запрещён; контент-менеджер не меняет торговые таблицы напрямую.

Предлагается одна новая PostgreSQL-база с одной схемой public и префиксами таблиц ar_. Отдельные DB-роли: миграции, CMS-контент, торговый сервер, чтение опубликованного каталога. Ограничения CMS на уровне прав приложения дополняются SQL-правами на торговые записи. Не использовать несколько схем одной БД для Directus. Redis/поисковый сервис пока не нужны; поиск около 100 товаров начать с PostgreSQL.

## Модель данных

| Область | Сущности и ограничения |
|---|---|
| Идентификаторы | UUID для бизнес-сущностей во всех слоях и fixtures; артикул — отдельная уникальная строка владельца; slug — строка, не UUID |
| Категории | category(parent_id, level, slug, status, sort); уровни раздел/категория/подкатегория; запрет циклов; связи product_category; CMS управляет деревом и навигацией |
| Товары | product(kind=single/bundle, title, slug, description, meta_description, seo_title, status); у single минимум один физический SKU, у bundle нет складского SKU |
| SKU | product_id, article, price_kopecks, media/attribute overrides, package_id; цена неотрицательная; общие фото/характеристики наследуются, переопределения явные |
| Характеристики | attribute(type, unit, filterable), attribute_value, category_attribute, product_attribute, sku_attribute; админка добавляет определения/значения/применимость, UI строится из метаданных |
| Автомобили | make, model, generation/modification; Приора 1/2 различаются; правило совместимости задаёт автомобиль, диапазон лет, кондиционер: yes/no/any/unknown |
| Совместимость | product_fitment и явное SKU-переопределение; результат compatible/incompatible/unknown. Отсутствие данных не означает «подходит всем». Комплект совместим только если подходят все компоненты; конфликт → incompatible, нехватка сведений → unknown |
| Комплекты | bundle_component(bundle_id, physical_sku_id, quantity>0), discount_bps 0..10000. Только физические SKU, без вложенных комплектов и клиентского изменения состава |
| Склад | stock(sku_id, on_hand, reserved), stock_movement, allocation; on_hand>=reserved>=0. Команды прихода/корректировки с причиной и сотрудником; корректировка не может нарушить активный резерв |
| Корзины/заказы | server_session, cart(version), cart_line, checkout_attempt, order(type, status, payment_status, shipping_status), order_line, order_component_snapshot, order_event |
| Оплата/доставка | payment_attempt, provider_event(inbox), shipment, shipping_quote, package_rule, shipping_event, manual_override; суммы/версия расчёта/сроки, ID провайдера, источник изменений |
| Доступ | customer, email_challenge(code_hash, expires_at, attempts), customer_session; подтверждение владения email отдельно от email в заказе |
| Контент | page, article, blog_category, tag, article_tag, external_video(provider, url, metadata), redirect_history; только VK/Rutube, без хранения видео |
| Социальные функции | favorite(customer_id, product_id) unique; review(customer_id, purchased_product_id, order_line_id, moderation_status), private_review_media |
| Надёжность | command_dedup(actor, key, request_hash, result), inbox(provider,event_id) unique, outbox, worker_job, audit_log |

Исторические order_line/component snapshots сохраняют названия, артикулы, цены, состав, скидку, совместимость и доставку на момент заказа независимо от дальнейшего редактирования каталога. Персональные сведения доступны только уполномоченным ролям и покупателю своего заказа.

## Цена, фильтры и наличие

Денежные расчёты — целые копейки. Предлагаем скидку хранить в базисных пунктах (0,01%), итог округлять half-up один раз после суммы price×quantity по компонентам; правило техническое, тестируется на границах. Цена комплекта производная, не редактируемая отдельная цена. Доступность = min(floor(доступный остаток SKU / его количество)); при повторении SKU сначала суммировать количества.

Фильтры цены, наличия и атрибутов должны совпадать на одном SKU (один EXISTS по исполнению), иначе товар не подходит. URL /product/:slug?sku=:id сразу SSR-рендерит выбранный SKU и проверяет принадлежность товару. Для комплекта переключателей исполнений нет.

## Контракты команд

- Все изменяющие команды получают server actor, idempotency key и проверенный payload. Один ключ с другим payload отклоняется; повтор возвращает сохранённый результат. Клиент не назначает цену, сотрудника и владельца заказа.
- Catalog query возвращает опубликованные карточки, варианты, трёхзначную совместимость, актуальную серверную цену и применимые фильтры.
- Checkout(cart_version, delivery_input, key) атомарно создаёт одну пару обычный/предзаказ и snapshots; повтор не создаёт новые заказы. Сервер возвращает суммы, состояние расчёта доставки и сроки.
- ConfirmPreorder(order_version, confirmed_terms, delivery_quote, key) проверяет права, полное наличие, актуальность итогов и возможность оплаты. По умолчанию подтверждать только после уточнения доставки, чтобы 30 минут были реальным сроком оплаты.
- StockReceive/Adjust/Cancel, ApplyPaymentEvent, ApplyShippingEvent и ExpireAllocation используют те же ограничения транзакций и журнал событий.
- Адаптеры Payment, Shipping, Mail, OwnerNotification, DescriptionGeneration изолированы от домена. Локальные реализации не вызывают реальные сервисы; внешний вызов выполняется после commit через outbox.

## Транзакции склада

Обычный заказ: раскрыть комплекты в физические SKU, объединить спрос с отдельными деталями, блокировать складские строки в стабильном порядке, проверить доступность и зарезервировать всё одной транзакцией. Резерв 30 минут. Оплата до срока превращает резерв в списание; отмена/истечение освобождают резерв ровно один раз.

Предзаказ: до подтверждения менеджером нет резерва или списания. При подтверждении все физические SKU должны быть доступны; одной транзакцией списывается весь состав и устанавливается expires_at=confirmed_at+30 минут. Оплата не списывает повторно. Неоплата возвращает весь списанный состав однократно. Для одиночного отсутствующего SKU предлагается тот же механизм, что и для комплектов.

Платёж и worker блокируют один order/allocation и атомарно сравнивают статус/срок. Событие после истечения/возврата → manual_review, без автоматической отправки и повторного списания. Повторные события и повтор worker безопасны. Время серверное UTC, интерфейс показывает срок покупателю.

Смешанная корзина — два заказа и два расчёта/платежа доставки. Недоступный комплект целиком уходит в предзаказ. Частично доступное количество одной строки и конкурирующие строки с общими SKU требуют продуктового правила; предлагаем целую строку в предзаказ и стабильный приоритет строк корзины с показом разделения до подтверждения (вопрос в status.md).

## Доставка и статусы

Исходный город Махачкала, СДЭК ПВЗ/курьер, без самовывоза. Масса и габариты упакованных SKU и проверенные правила коробок — данные CMS. Размеры смешанной посылки не суммировать механически. Отсутствие правила/сбой API → delivery_pending, стоимость null, оплата закрыта. Менеджер уточняет стоимость, покупателю показывается новая полная сумма; платёж создаётся на эту версию расчёта.

Предложение конфликта статусов: ручная корректировка включает explicit override с причиной. События перевозчика продолжают записываться, но не меняют публичный статус до снятия override сотрудником. Повторные/старые события не откатывают состояние. Оплата и доставка — разные состояния; факт получения для отзыва берётся из доверенной истории, а не заявления клиента.

## Безопасность и контент

Сессия в HttpOnly/SameSite cookie, Secure на HTTPS; CSRF/origin-проверки, лимиты запросов. Номер заказа не является ключом доступа. Предложение email-кода: 10 минут, 5 попыток, повторная отправка не чаще 60 секунд с суточным лимитом; хранить hash, одноразово погашать, исключить перебор/утечку существования email. Проверить эти значения при реализации.

Избранное объединяется по множеству product_id, без потери сохранённого списка. Отзывы — после получения купленного товара и модерации. Начальные пределы брифа: до 5 фото по 10 МБ; предложены JPEG/PNG/WebP и максимум 24 Мп. Проверять действительный формат, декодирование, ресурсы, частоту и общий размер; перекодировать, удалять метаданные; исходники и неодобренные файлы приватны.

Генерация описаний: только проверенные поля товара, серверный ключ, без данных покупателей; draft двух полей → редактирование → Apply с проверкой версии товара; title не менять. До отдельного разрешения — имитация, без платных вызовов.

Каталог сначала читать без общего кеша; оптимизацию добавлять после измерения, с инвалидированием после CMS. Заказы/сессии/корзины всегда private, no-store. HTML контента санитизировать; внешние video URL проверять по разрешённым провайдерам.

## SEO-маршруты

Полные требования и тесты: [06-seo-plan.md](../new-store-kit/06-seo-plan.md). Ниже проектная матрица для будущей публичной версии; локально все страницы noindex, сервисы доступны только локально.

| Маршрут | Индексация / canonical / HTTP |
|---|---|
| Главная, опубликованная категория, полезная автомобильная подборка | index, self canonical, 200 |
| Каталог page=2 и далее | index при существовании, собственный canonical, HTML-ссылки пагинации |
| Товар /product/:slug | index, self canonical; отсутствие остатка не равно удалению |
| ?sku=:id | SSR выбранного SKU; canonical базовой карточки; отдельная индексация только после обоснования |
| Поиск, произвольные фильтры и сортировка | noindex; нормализованный URL, без sitemap; не блокировать чтение noindex через robots |
| Статьи и полезные архивы блога | index/self; пустые/тонкие архивы noindex |
| Корзина, checkout, кабинет | noindex, private/no-store; контроль доступа, не sitemap |
| Старый slug | 301 сразу на текущий canonical без цепочки |
| Несуществующая сущность/страница пагинации | 404; пустой поиск отдельно 200/noindex |

Product/Offer, ProductGroup, BreadcrumbList, Article, VideoObject — только по фактам и типу страницы; без рейтингов. Sitemap только канонические index URL. YML и JSON-LD согласованы с SSR, включая предзаказ. Валидаторы и официальные рекомендации повторно проверить перед запуском.

## Изоляция и эксплуатация

Планируемый namespace autoreelz2026-new; новая БД autoreelz2026_new и отдельная autoreelz2026_test; собственные сеть/тома/учётные записи/секреты. Предложены localhost-порты 14321 (Astro), 28055 (CMS), 65432 (PostgreSQL при необходимости host-доступа). Перед запуском проверить занятость снова. Существующие 4321/4323/5432/55432/8055/18055 не использовать.

Миграции БД и snapshot метаданных Directus версионируются согласованно; схему изменяет один ответственный. До реального выпуска — backup/restore на отдельной базе, мониторинг просроченных jobs, ошибок API, manual_review и outbox. Релиз фиксирует SHA, lockfile, digest образов и миграционную ревизию.
