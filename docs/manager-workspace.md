# Рабочие разделы кабинета

Согласовано30.09.2026: разделить длинную страницу «Заказы и склад», применить светлую оболочку обзора ко всему кабинету.

- `/manager` — показатели/график, задачи, последние5 заказов, короткое предупреждение о низких остатках/незаполненных товарах. Полные таблицы находятся в своих разделах.
- `/manager/orders` — список по20, поиск по номеру/покупателю/контактам, тип, статус оплаты и доставки, очередь задач, даты МСК. Фильтры/страница вURL. Возврат из заказа сохраняет их и позицию прокрутки; контакты/поиск не складываются вlocalStorage.
- `/manager/orders/[id]` — только один заказ: состав, получатель, доставка, существующие команды, заметки и история. Серверные транзакции, проверки и идемпотентность не меняются.
- `/manager/stock` — все исполнения с поиском и фильтрами, таблица с on_hand/reserved/free. У выбранногоSKU: приход, корректировка и история движений. Формы вdialog, обязательная причина, защита от потери незаписанного ввода; закрытие возвращает фокус. Не уменьшать ниже действующего резерва. Порог низкого остатка — предпочтение браузера. У комплектов собственного остатка нет.
- `/manager/products` — каталог и готовность, явные ссылки редактирования вCMS. Редактор Directus не дублируется.
- `/manager/reviews` — прежняя модерация в общей оболочке.
- `/manager/content` — статьи/страницы со ссылкамиCMS и переход к описаниям; существующий генератор переезжает в`/manager/descriptions`.
- `/manager/service` — уведомления/тестовая почта по вкладкам, загружаются отдельно и только после проверки прав.

Общее меню с активным разделом, на телефоне раскрывается кнопкой. В рабочем кабинете нет шапки витрины с корзиной. Вход/выход иCSS-модель сохраняются; возврат изbfcache перечитывает защищённые данные. Старые`?order=`/`?sku=` и`#manager-*` переходы переводятся на новые маршруты.

Новые GET `order-list`, `order`, `inventory`, `stock-history`, `catalog-readiness` под существующим staff/no-store. Параметры валидируются, SQL — с параметрами; списки с пагинацией. Ни миграций, ни перезагрузки каталога, ни изменений платежей/доставки. Проверки мутирующих команд — только изолированнаяQA-база/подменённыйAPI, рабочие заказы и склад при приёмке не менять.
