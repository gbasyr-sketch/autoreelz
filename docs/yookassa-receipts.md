# Передача данных для «Чеков от ЮKassa»

Подготовлено и опубликовано15.10.2026 по отдельным поручениям владельца. Это передача данных и проверка регистрации: чек формирует и отправляет покупателю сама ЮKassa. Собственный SMTP и отправка магазином не нужны. Анкета рабочего магазина находится на проверке — основание: предоставленный владельцем экран. 15.10 услуга подтверждена экраном рабочего кабинета; фактические платежи и фискализация сайта не проверялись. Рабочий контур и закрывающие чеки035 опубликованы с выключенными реальными операциями: [актуальный контракт](yookassa-production.md).

## Границы этой доработки

Сайт сохраняет состав чека вместе с новой попыткой оплаты, передаёт его в `receipt` при POST `/payments` и отдельно проверяет `receipt_registration` платежа/полного возврата. Реальные деньги, production и отправка фискальных документов не включались. Событие успешной оплаты не означает успешную регистрацию чека.

Согласованные данные: ИП, УСН «Доходы» 6%, без НДС, сервис «Чеки от ЮKassa». Налоговая система должна быть настроена и подтверждена в рабочем кабинете; неподтверждённый `tax_system_code` в API не добавляется. `vat_code=1` означает без НДС. Получатель — email из неизменяемого заказа; телефон/имя и другие ненужные контакты не передаются в receipt.

Владелец уточнил процесс: при отсутствии товара сначала проверяет наличие у поставщика, затем подтверждает заказ и просит полную оплату. Неподтверждённый предзаказ по-прежнему нельзя оплатить. При оплате до получения товара документация ЮKassa называет способ расчёта `full_prepayment`; это не аванс за неподтверждённое наличие. Процесс подтверждения заказа этой доработкой не меняется.

## Контракт

- Источник — только серверный заказ, не тело запроса браузера и не текущий каталог. Название с исполнением (до128 символов), положительное целое количество, точная цена единицы в RUB; комплект остаётся одной продаваемой позицией. Состав физических SKU в чек не разворачивается.
- Доставка с положительной ценой — отдельная услуга. Бесплатная доставка отдельной нулевой строкой не передаётся. Все позиции без НДС, `full_prepayment`; интернет-расчёт, часовой пояс Москвы. Максимум80 строк вместе с доставкой.
- Проверяются email, цены/количества, суммы строк, сумма товаров и полный итог платежа. Неверный состав блокирует создание попытки оплаты до внешнего POST. Поля API собираются по разрешённому списку.
- `receipt_snapshot` записывается атомарно с платежом до сети и запрещён к изменению триггером028. Существующие платежи не дополняются задним числом. Повтор использует прежние снимок, ключ и тело; старые ограничения lease/23часов сохранены.
- `YOOKASSA_RECEIPTS_MODE=disabled` по умолчанию сохраняет прежнюю песочницу без фискализации. `yookassa` — явное включение подготовки снимков только в существующем test-контуре. Перед POST GET `/me` проверяет свой test-магазин и соответствие включённой фискализации наличию сохранённого снимка. Флаг сам по себе услугу не подключает. Рабочие ключи не принимаются прежними предохранителями.
- Статусы денег и чека хранятся отдельно. Неизвестный/отсутствующий статус чека не маскирует проверенный успех оплаты. Worker после завершения денежной операции выполняет только проверенные GET известных IDs, включая успешные платежи/возвраты. Неверные ID/сумма/магазин не принимаются. Новый платёж из-за ошибки чека не создаётся.
- Переходы регистрации записываются в историю заказа однократно; `canceled` требует ручной проверки. После трёх дней неподтверждённого результата появляется событие обращения в поддержку; GET продолжается раз в день. Последующий успешный ответ может завершить сверку. Терминальный фискальный результат не откатывается запоздалым pending.
- Для полного возврата адаптер проверяет наличие исходного снимка, GET исходного платежа и свой test-магазин. Новый receipt в POST возврата не отправляется: по контракту сервиса используется исходный чек. Денежный успех возврата и регистрация его чека различаются; физический склад не меняется.

## Что ещё не готово к реальным продажам

Код production-интеграции и закрывающих чеков уже опубликован035, услуга подтверждена экраном. Остаются рабочие ключи/сверка условий кабинета и отдельное разрешение контролируемой реальной оплаты/чека/возврата. Текущая песочница с fiscalization_enabled=false не подтверждает работу именно этой услуги.

Документация ЮKassa также требует чек зачёта предоплаты при выдаче товара. Его очередь/событие выдачи и отправка в эту доработку не входят. Нельзя считать отправку СДЭК получением товара. Частичные возвраты, возвраты после выдачи и завершение спорных заказов остаются отдельной работой. Это подготовка данных для чека при оплате, а не завершённая фискализация всего жизненного цикла.
