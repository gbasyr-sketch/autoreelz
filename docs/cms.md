# Локальная CMS и Docker-среда

Этап 3. Только новый проект AUTO REELZ. Старые базы, контейнеры и Directus MCP не используются.

## Адреса

| Сервис | Адрес |
|---|---|
| Новая Directus CMS | http://127.0.0.1:28055/admin |
| Витрина в Docker | http://127.0.0.1:14323/ |
| Локальная Astro-разработка | http://127.0.0.1:14322/ |
| Новая PostgreSQL | 127.0.0.1:65432, база autoreelz2026_new |

Витрина пока использует fixtures этапа 2. Подключение каталога CMS к витрине относится к этапу 4; изменение карточки в CMS сейчас не меняет storefront.

## Учётные записи

В `.env` находятся ADMIN_EMAIL / ADMIN_PASSWORD и EDITOR_EMAIL / EDITOR_PASSWORD. Файл создан с правами 0600, исключён из Git. Секреты не копировать в документацию/чат/скриншоты. Адреса с example.com — локальные технические аккаунты, письма им не отправляются.

- Владелец: администратор CMS, доступ к настройкам и каталогу.
- Контент-менеджер: создание/чтение/редактирование каталога, справочников и медиа. Может удалять ошибочные связи состава/характеристик/фото. Не управляет ролями, схемой и складом.
- Публичный доступ к коллекциям не выдан. Будущий сервер витрины получит отдельный ограниченный доступ.

По предпочтению владельца админка использует светлую тему независимо от темы ОС. Она установлена по умолчанию для проекта и явно для двух локальных аккаунтов, а также закреплена в configure-cms.mjs.

Cookie новой CMS называются autoreelz2026_new_session и autoreelz2026_new_refresh, чтобы не пересекаться с другими локальными Directus. Secure=false используется только для локального HTTP; перед публикацией нужен HTTPS и Secure=true.

Directus показывает запрос реального владельца проекта и принятия MSCL/DPA. Он отложен штатной кнопкой Remind Later. Условия от имени владельца не принимались, заявка на грант/платный тариф не отправлялась. Перед реальным запуском проверить лицензию выбранной версии, функции/лимиты и завершить этот шаг самостоятельно.

## Первый запуск на новом компьютере

Нужны Docker с Compose, Node 24.21.0, npm 11.19.1 и Python 3. Из корня:

```sh
node scripts/setup-local.mjs --seed-demo
```

Скрипт создаёт независимые секреты, проверяет Compose без вывода секретов, собирает витрину, запускает сервисы, применяет SQL-миграции, настраивает CMS и добавляет демоданные. Существующая `.env` не перезаписывается. Повторное заполнение не заменяет изменённые записи/остатки. Без `--seed-demo` данные не добавляются.

Для текущего компьютера доступен локальный Node:

```sh
.tools/node-v24.21.0-darwin-arm64/bin/node scripts/setup-local.mjs
```

Все скрипты ограничены project autoreelz2026-new и базой autoreelz2026_new. Отдельный db-init выполняет создание ролей после готовности PostgreSQL; это устраняет зависимость от executable-флагов bind-mounted файлов macOS.

## Запуск и остановка

```sh
docker compose -p autoreelz2026-new up -d
docker compose -p autoreelz2026-new ps
docker compose -p autoreelz2026-new stop
```

Остановка сохраняет данные. Не применять `down --volumes` к рабочей среде: это удаляет её новые тома. Не запускать команды без проверки имени проекта. При изменении `.env` существующие пароли БД автоматически не ротируются; это отдельная операция, не повод удалять том.

## Хранение и границы прав

- Проект/сеть/тома имеют префикс autoreelz2026-new; порты привязаны только к 127.0.0.1.
- database хранит PostgreSQL; uploads — файлы нового Directus.
- ar_migrator владеет доменными таблицами и применяет миграции.
- ar_cms владеет системными таблицами Directus, получает CRUD каталога и только SELECT остатков. Не может ALTER/DROP доменную схему или менять ar_stock.
- ar_app зарезервирован для торгового сервера, пока получает только чтение доменных данных. Реальные торговые команды — следующий этап.
- ar_catalog_reader подготовлен как отдельная учётная запись; публичный доступ и использование витриной пока не включены.

Образы PostgreSQL 17.11, Directus 12.3.1 и Node 24.21.0 закреплены digest. Витрина запускается от непривилегированного пользователя node, файловая система контейнера read-only. Docker-контекст ограничен исходниками/публичными ресурсами/lockfile; секреты, PDF, Git и локальные runtime в образ не входят.

## Модель каталога

- Категории: управляемое дерево до трёх уровней, запрет циклов и переноса поддерева за пределы глубины.
- Товар: название, slug, вид, основная/дополнительные категории, публикация, описание, отдельные ручной SEO-title и meta description.
- SKU: уникальный существующий артикул, отдельная цена в целых копейках, фото и совместимость с режимами наследования/замены. Артикулы не перенумеровываются. Владелец SKU фиксируется при создании.
- Характеристики: определения select/text/number/boolean, справочник значений, применимость/фильтрация по категории, общие значения товара и переопределения SKU. Тип используемой характеристики и родитель используемого значения защищены.
- Совместимость: автомобиль, поколение/модификация, годы, кондиционер, состояния «не подтверждено / подходит / не подходит». Нет правила — неизвестно. Тип отопителя не добавлялся.
- Комплект: конкретные физические SKU с количеством, без собственного SKU/склада. Скидка в CMS задаётся обычными процентами (numeric(5,2)), не базисными пунктами. SQL ar_bundle_offer вычисляет цену в копейках и доступность по общим остаткам.
- Фото: общие/индивидуальные связи с Directus Files. ar_effective_sku объединяет характеристики и выбирает фото/правила по режиму наследования.
- История slug записывается автоматически. Единый реестр текущих/прежних адресов защищает от повторного захвата адреса другим объектом, в том числе конкурентного.

Демокаталог: 3 отдельных товара, 7 SKU, 1 фиксированный комплект, 2 автомобиля (Приора 1/2). Материалы и совместимость не выдаются за факты; массы и габариты не придуманы. Заказы, резервы и складские команды не реализованы этим этапом.

## Как работать с формами

1. В «Товары» открыть карточку, изменить текст, нажать верхнее «Сохранить», открыть снова для проверки.
2. Для нового товара заполнить название, slug, вид и категорию. В панели выбора связанной записи выбрать строку и нажать её «Сохранить», затем сохранить основную карточку.
3. Добавить SKU через «Исполнения товара → Создать» либо раздел «Исполнения (SKU)». Цена 490000 копеек означает 4 900 ₽; использовать фактический артикул владельца.
4. Общие характеристики и фотографии находятся в товаре. В SKU добавлять только переопределения; для собственных фото переключить режим на «Собственные фотографии».
5. В «Совместимость» не выбирать «Подходит» без данных. Приора 1 и Приора 2 выбираются отдельно, модификация должна принадлежать выбранному автомобилю.
6. Для комплекта выбрать вид «Готовый комплект», затем связать нужные SKU и количество. Цвет самого комплекта не переключается: он определяется выбранными компонентами.
7. Новые фильтры создавать записями раздела «Характеристики» и связью с категорией. Не менять SQL-схему через Settings для каждого нового признака.
8. Остатки пока только читаются. Приход/корректировка с историей и защита от повторов будут добавлены на торговом этапе.

## Миграции и проверки

```sh
node scripts/migrate.mjs
node scripts/configure-cms.mjs
node scripts/export-cms.mjs
node tests/cms-schema.mjs
node tests/cms-permissions.mjs
node tests/cms-browser.mjs
```

Применённые SQL-файлы защищены SHA-256: изменять их нельзя, добавляется следующая миграция. Повторный запуск пропускает совпадающие миграции. SQL-схема — источник истины, model.mjs описывает формы/отношения/права. schema.snapshot.json — проверяемый экспорт метаданных, не инструкция бесконтрольно перестраивать БД.

Directus 12 API изменения отношений пересоздаёт внешние ключи. Поэтому configure-cms обновляет только directus_relations через владельца миграций; определения FK, ON DELETE и владение таблицами сохраняются. После настройки отношения перечитываются перезапуском только новой CMS.

SQL-тесты используют временную ar_qa_* копию только новой БД и удаляют её в finally. Сырые дампы/токены в Git не попадают. Браузерная проверка отдельно покрывает реальное создание/сохранение/повторное открытие форм.

Для реального релиза ещё нужны резервное копирование/восстановление, HTTPS, мониторинг, миграционная стратегия отката и привязка образа к проверенному commit SHA; локальный этап не объявляется готовностью к продажам.

Браузерному тесту нужен Playwright: по умолчанию используется bundled runtime Codex на текущем компьютере; путь можно передать через PLAYWRIGHT_MODULE. Он создаёт помеченные QA-записи и удаляет их в finally. Запускать на локальном демокаталоге, не на реальных данных.
