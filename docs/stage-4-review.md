## Исправлено при проверке

- Повторное failed-событие старой попытки оплаты больше не сбрасывает pending новой попытки. Смена доставки проверяет реальные ожидающие платежи под блокировкой заказа.
- Скрытая категория компонента исключает комплект из покупки, как и неопубликованный компонент.
- Запросы внутри одного PostgreSQL-клиента выполняются последовательно; счётчик истечений учитывает только завершённую транзакцию.
- Directus получил 26 активных коллекций при лимите Core 25 и заблокировал вход редактора. Необязательная Studio-коллекция ar_order_components выключена штатным API статуса, без удаления таблицы/данных. Теперь /license active, 25/25, обе роли входят. Решение проверено повторным браузерным прогоном и чтением метаданных; setup сохраняет его.

Независимая проверка исправлений не выявила оставшихся блокеров этапа 4. Временные QA-базы и процессы удалены; старые проекты не использовались.

## Не проверено и следующий этап

Это приёмка одного локального сценария, не всего MVP. Полный fresh bootstrap с миграциями 004/005 на пустых Docker-томах отдельно не повторялся: миграции применены к новой среде этапа 3, свежий bootstrap которой проверен ранее. Торговые тесты использовали изолированные базы; Docker-сборка, запуск worker и повторная настройка торговых форм прошли.

Этап 5 ещё не начат: CMS-страницы/блог, синхронизация избранного, отзывы и обработка фото, генератор описаний, расширенная CRM, трек-номер/события перевозчика, MAX и руководство. До расширения CMS нужно решить объём коллекций: текущий Core занят на 25/25. Юридические условия и платные планы без владельца не принимаются.

До реальных продаж остаются реальные товары/упаковка/совместимость, реквизиты, проверенные тексты, реальные адаптеры, лицензия, HTTPS, backup/restore, мониторинг и полная приёмка этапа 6. Локальные Chrome-проверки не заменяют физические устройства, нагрузочное тестирование и реальные метрики покупателей.
